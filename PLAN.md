# Local co-op for Deep Rock Galactic: Survivor - plan

Replaces the network prototype (`drg-survivor-coop`, kept public as an experiment). Idea: **one game
instance, two real dwarves** (second controller), online through Steam Remote Play Together. One
simulation, so nothing can drift apart.

## Decisions (owner, 2026-10-21)

1. A dwarf that dies: the run is lost for now (revive stays an option for later).
2. Level-ups are shared and answered one after the other.
3. One camera frames both dwarves, zooming out with distance up to a maximum (to be tested).

## Phases

| Phase | Goal | Done when |
|---|---|---|
| 0 | Floor: plugin, state dump, in-game screenshots, auto start, crash test | `lc-run.ps1` PASS, twin FAIL (below) |
| 1 | **Feasibility:** a second real `Player` in one instance | dwarf 2 walks (controller 2), shoots, takes damage, dies; an enemy targets the nearer dwarf; level-up survives. Stop rule: three reasoned attempts, then document the cause and go to the network route |
| 2 | Playable core | whole Elimination run with two controllers, shared XP and cash, camera on both, shared level-up, run lost when a dwarf dies |
| 3 | Online by Remote Play Together | the owner plays with a second person; report picture quality and delay |
| 4 | Content | escort, boss, drop pod, second biome, HUD polish |

## How it is tested (rules)

- Every check has a twin that must turn it red (switch off or break the thing).
- No test switch in the shipped path: test behaviour lives behind `-lc...` flags that a normal launch never sets.
- A green automated run is **not** acceptance. Each phase ends with a short owner checklist (max 10 lines).
- Layers: (1) `lc-state.jsonl`, one JSON line per second, tests read only this; (2) scripted input injected
  from inside the plugin; (3) screenshots from inside the game (`ScreenCapture`), judged by the launcher
  for black/flat frames and looked at by the agent; (4) crash/regression smoke; (5) owner checklist.

## Phase 1 result (2026-10-21, evening) - second dwarf works in one instance

Recipe that makes the clone a working player (all in `Phase1.cs`, behind `-lcp1=`):
1. Instantiate the live dwarf under an **inactive** parent, `DiContainer.InjectGameObject`, activate it next to the first.
2. `SetupBaseStats(original._baseStats)` (gives hp/speed stats), then `currentHp`.
3. `CreatePlayerMovement<WalkPlayerMovement>()` and `CreatePlayerAnimator<WalkPlayerAnimator>()`, then `Init(clone, gfx, original.classArtifactData)` on both, and copy `classArtifactData` (the movement object had no rigidbody and no artifact data before).
4. Control type to `FULL_CONTROL` by writing the field (`SetMoveControlType` is asynchronous and did nothing for the clone), then write `moveDir` each frame. `rawMoveInput` and `ForceMove` do **not** drive it.
5. `EquipNewWeapon(original.weapons[0].data)` and tick the clone's weapons with `DoUpdate(deltaTime)` (the game's own tick does not reach them).
6. Enemy targets: an enemy chases through **four** references, all must be written through the pointer with the GC write barrier (the interop setter of `Enemy.player` does not work): `Enemy.player`, `BaseEnemyBehaviour.target`, `AIMeleeSkillHandler.player`, each `AIWeaponHandler.target`. Rule used: the nearer living dwarf.
7. Clone must not inherit test switches (`GOD_MODE` was copied from the original).

## Design decisions, part 2 (owner, 2026-10-21 evening): HUD, currencies, shop

- **HUD:** two separate bottom panels. Left P1, right P2. Each shows a label (P1 / P2), the hp bar above and the four weapon slots (1-4) below. The existing bottom HUD is reused as the template for the second panel.
- **XP:** shared (one level for both). Level-ups answered one after the other (earlier decision).
- **Currencies:** shared in stage 1 and identical for both. **Spending is per player:** each dwarf gets its own shop that mirrors the currency. After the first shop the wallets are separate, so dwarf 2 can start stage 2 with more if they spent less. From then on the currency display needs a P1 / P2 variant.
- Open points to settle before building (asked in chat): do pickups credit both wallets in full after the split; are the two shops shown one after the other or side by side; where the P1/P2 currency display goes.
- **Settled (owner):** (1) after the split every pickup credits **both** wallets in full, only spending differs; (2) the two shops are shown **one after the other** (P1, then P2); (3) the currency display becomes **two lines, P1 / P2** once the amounts differ.

## Phase 2, step 1 result (2026-10-21, night): input separation and camera

**Input routing** (`InputRouting.cs`): the clone subscribes to the same global input actions as the original (confirmed by the function map: `Player.Start` subscribes, `OnMoveInput/OnMoveStarted/OnMoveEnded` only act when the control type is FULL_CONTROL). Three Harmony prefixes on those callbacks decide by `ctx.control.device`: input from player 2's device (virtual pad in tests, otherwise the second real gamepad) reaches only the clone, input from every other device only the original. The clone is then driven by the game's own code, including the camera rotation of the input. The patched methods only run on input events, so they are installed together with the clone (never during title-scene startup).
- Before: pad 2 moved both dwarves (`20261021-204255-p1-clone-pad`: host span 19.8 m). Disabling the device (keepSendingEvents) did **not** help (`20261021-205420`).
- After: right, left, up all work for the clone and the host stays put: `20261021-211101-p1-clone-route` (right, left, up; host at 30.5/28.6 throughout); first routing run `20261021-205710-p1-clone-route`. The clone stops only at walls (it came back when the stick reversed).

**Camera** (`Cam2.cs`, port of the prototype's focus + dolly variant): Follow target of the Cinemachine virtual camera becomes the midpoint of the living dwarves, the transposer offset is scaled with their distance (free below 10 m, +1.0 per 25 m, maximum 2.2x). Original follow/offset restored when the clone is gone. `-lcnocam` is the vanilla twin.
- Acceptance run `20261021-211532-p1-clone-cam`: both dwarves on screen in 100% of the settled frames at 6, 12, 18, 24, 30 and 36 m (about 46 frames each).
- Twin `20261021-211654-p1-clone-cam` (`-lcnocam`): 100% up to 18 m, **0%** at 24, 30, 36 m. So the test can fail.
- Open: the zoom limit is not tested beyond 36 m; the camera shake/zoom coroutines of the game (`SetOrthoSize`, `ZoomLoop`) were not exercised; the owner has to judge how it feels.

## Phase 2, step 2 result (2026-10-21, night): HUD with two panels, and the screen-edge limit

**HUD** (`Hud2.cs`, `HudPatches.cs`). The game's bottom bar is `UICoreFront` (not `UICoreForm`): `actionBarGroup` is a full-width strip (`PlayerUI`, 1920 px) whose children are `Bar (Health)` (568 px) and `Main Slots`. The strip is duplicated once; in each copy the two children are moved to the left/right (about +-330 px), so P1 stands left and P2 right. "P1"/"P2" labels are copies of the hp text. The right panel is filled from the clone: hp fill and text, and each weapon slot through `UIActionBarSlot.Setup(data, handler)`.
- Interop notes: `Transform` must be turned into `RectTransform` with `GetComponent`, a C# cast throws; `GetWorldCorners` fills a managed array with zeros (use `TransformPoint`).
- **Leak found and fixed:** the game's own HUD handlers listen to global events, so the clone's damage, heal and weapon events landed in the LEFT panel (it showed the clone's hp and a second pistol). Harmony prefixes drop `UICoreForm.OnPlayerDamageTaken/OnPlayerHeal/OnPlayerWeaponEquipped/OnPlayerWeaponRemoved` when the event belongs to the clone (installed with the clone). `Player.Awake` also overwrote `RunSettingsManager.player` with the clone; it is given back to the original (that alone did not fix the panel, the event drop did).
- Acceptance `20261021-214012-p1-clone-hud`: P1 text `LP: 145 / 145`, P1 shows exactly the original's 1 weapon, P2 right of centre with its own hp fill (0.71 after 60 damage) and its weapon, bars at -6 / +6 world units around the centre.

- The owner looked at a screenshot and says the UI looks good.

**Screen-edge limit / zoom maximum** (`Cam2.cs`, owner request). The zoom has a maximum (`KMax` 2.2). At maximum zoom the screen is the limit: when one dwarf would leave the margin (8% of the viewport), the dwarf that moved most this frame is stopped: if it moved away, its step is taken back (it stays at the edge, nothing is dragged through rock); otherwise it is pulled toward the other in small steps. First attempts that pulled in a straight line got stuck in terrain; teleporting a clone into rock flings it hundreds of metres (the test now walks it along the longest free NavMesh line).

## What the other agent's decompile (FUNCTION-MAP section 11) settled
- Input: `Player.Start` subscribes only Move (3 callbacks), DriverAccelerate (3) and RockAndStone; aiming and shooting are automatic (`WeaponHandler.UpdateTarget`), the right stick is not an aim path. So routing Move is enough.
- Level-up card: `UISkillButton.OnButtonClick` applies the skill to `UISkillButton.player` (+0x320); `LevelUpManager.player` only steers the flow, so the dwarf can be swapped per card.
- Pickups: `Pickup.player` (+0x38) decides who gets xp/gold, not the collider. P2 only collects when it is set to P2.
- Wallet: second wallet can be hung into `UIShopButton.wallet`, `UIShopScreen.wallet`, `UIButtonPrice.wallet`, `UICurrencyGroup.Setup(..., secondWallet, ...)`. Caveat: `Wallet.OnCurrencyChanged` is static and `saveDataManager` is shared.
- P2 class: `Player.PrepareCoreRunStarted` reads `RunSettingsManager.selectedClass/selectedClassMod`; set them to the P2 class temporarily, or give P2 its own manager.

### Phase 2, step 3 result: shared XP, level-ups one after the other, pickups for P2 (2026-10-21, night)
Code: `LocalCoop/Share.cs` (Harmony patches installed with the clone + `LevelRounds`). Rules:
- XP is one pool: `Player.GainXp` on the clone is forwarded to the host (counter `XpRedirected`); the host owns the level.
- Pickups belong to the dwarf that touches them: `Player.OnTriggerEnter` sets `Pickup.player` to the toucher (via `GetComponentInParent<Pickup>`; `GetComponent` found nothing), so the pickup flies to that dwarf; XP picked up by P2 is then forwarded to the host.
- Level rounds: every level the host gains is owed once to P2 (`LevelUpManager.OnPlayerLevelGain` postfix). When the game's own flow has ended for the host and nothing is queued, the same flow runs again with P2 as its player: `LevelUpManager.player`, `SkillCollectionManager.SetPlayer`, `UILevelUpForm.player` and every `UISkillButton.player` are set to P2 (private fields through `SetRef`), a `PlayerLevelGainArgs(P2, level)` is queued and `StartFlow()` called; everything is handed back when the flow is over. The game is paused all along, so nothing else can level.
- Harness: `AutoStart.PickCard` now clicks the card (`UISkillButton.OnButtonClick`, which applies the skill to the card's player), before it only called `OnSkillChosen` which applies nothing. A Harmony prefix on `OnButtonClick` records which dwarf each card went to.
Evidence:
